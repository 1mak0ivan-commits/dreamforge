# Правила работы для агента

## Контекст проекта: DreamForge

DreamForge — Telegram Mini App, AI-платформа для ролплея с персонажами и мирами
(вдохновлено character.ai).

**Стек:**
- Frontend: React + Vite
- Backend: FastAPI
- Хранилище: JSON-файлы (не БД)
- Локальные модели: Ollama (утилитарные вызовы), Stable Diffusion WebUI
  (генерация изображений — намеренно локально, без цензуры контент-фильтров)
- LLM для реплик персонажей: OpenRouter (DeepSeek) — гибридная схема:
  диалоги персонажей идут через OpenRouter, утилитарные/служебные вызовы —
  через локальный Ollama

**Реализованные фичи (после капитального ребилда проекта):**
- Стриминг чата через SSE
- Извлечение памяти и скользящая суммаризация (sliding summarization)
- Режим со-творчества (co-creation assistant mode)
- LLM-улучшенные промпты для изображений с визуальной идентичностью персонажа
- Групповые чаты
- Кинематографичные баннер-карточки миров

**Известные болевые места (были, возможно ещё актуальны):**
- Баг с утечкой лока (lock-leak)
- Проблемы с финализацией создания мира (world creation finalization)

**Стиль работы пользователя:**
- Общение и комментарии — на русском
- Прямой, ориентированный на эффективность подход
- Предпочитает решения максимального охвата, а не минимальные патчи
- Приоритет — чистый и корректный код, а не просто рабочий

## Обязательное ревью кода

Ты — основной агент, пишешь код с помощью инструментов (файлы, shell, и т.д.).
После **каждого значимого изменения кода** (новая функция, рефакторинг,
исправление бага, новый файл) — прежде чем считать задачу завершённой,
обязательно вызови subagent `reviewer` и передай ему:

1. Что именно ты изменил (диф или список файлов).
2. Краткое описание цели изменения.

Дождись ответа ревьюера. Если он указал на проблемы — исправь их и, если
изменения существенные, отправь на повторное ревью. Только после того как
ревьюер не нашёл критичных замечаний (или замечания мелкие/стилистические),
считай задачу выполненной и сообщай об этом пользователю.

Не вызывай ревьюера для:
- тривиальных правок (опечатки, форматирование, переименование переменной)
- вопросов, не связанных с написанием кода (объяснения, поиск информации)

## Формат запроса к ревьюеру

Пример вызова:

> Проверь этот код на баги, антипаттерны, проблемы безопасности и
> производительности. Контекст: [краткое описание задачи].
> Код/diff: [вставить]

## Стиль работы

- Пиши чистый, корректный код, а не просто рабочий — это приоритет.
- Если у ревьюера и у тебя разные мнения по неоднозначному вопросу —
  explain trade-offs пользователю, не решай молча в одну сторону.

## Git

После того как код прошёл ревью (см. выше) и задача завершена:
- Делай `git add` и `git commit` с осмысленным, кратким сообщением на
  русском или английском (commit message в стиле conventional commits,
  например `fix: исправлен lock-leak в chat.py`).
- **НИКОГДА не делай `git push` самостоятельно** — пользователь делает
  push сам, после того как проверит изменения. Это осознанное ограничение:
  промежуточный код не должен улетать в удалённый репозиторий без ручной
  проверки.
- Не делай `git commit --amend`, `git reset --hard`, `git push --force` и
  другие деструктивные операции с историей без явного запроса пользователя.
